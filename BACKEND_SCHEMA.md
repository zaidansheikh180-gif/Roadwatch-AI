## 1. Purpose and Scope

This document defines the proposed database structure, relationships, constraints, access policies, image-storage approach, and trusted backend operations for RoadWatch AI.

It is the intended data-model reference for frontend and backend implementation.

The schema supports:

- Anonymous and registered road-damage reports.
- Photograph references and geographic coordinates.
- Secure anonymous report tracking.
- AI screening attempts and their results.
- Separate report lifecycle and verification states.
- Administrative review and corrections.
- Report-status history and auditability.
- Public map data and clearly identified sample reports.

**Implementation status:** This document describes an agreed design baseline. It does not establish that the tables, policies, storage buckets, or functions already exist.

## 2. Design Principles

1. **Reports survive AI failures.** A valid report must not be discarded because screening fails, times out, or returns an uncertain result.
2. **Keep statuses separate.** Lifecycle, verification, and AI screening represent different concepts.
3. **Protect anonymous tracking.** A public report ID must not grant private tracking access or administrative privileges.
4. **Enforce security on the backend.** Frontend route protection and hidden buttons are not authorization.
5. **Expose only approved public fields.** Public map responses must never reveal account information, tracking-token hashes, or internal administrative notes.
6. **Record important changes.** Administrative status changes and corrections should be auditable.
7. **Distinguish sample data.** Demo-generated records must be distinguishable from genuine test submissions.
8. **Validate on the server.** Client-side validation improves usability but is not a security boundary.
9. **Avoid unsupported AI claims.** Store the model's actual output and uncertainty; do not invent a severity score or imply official verification.
10. **Keep the architecture consistent.** Supabase PostgreSQL, Supabase Auth, Supabase Storage, and Supabase Edge Functions where needed remain the approved MVP planning direction.

## 3. Proposed Data Model

The MVP uses five principal tables.

| Table | Purpose |
|---|---|
| `reports` | Main report, location, photograph reference, reporter association, and current states |
| `ai_screenings` | Individual AI screening attempts and results |
| `user_roles` | Backend-managed administrative roles |
| `report_status_history` | Audit trail of lifecycle and verification changes |
| `report_reviews` | Administrative review decisions, corrections, and rejection reasons |

Supabase Auth remains responsible for user identity and authentication. The schema references authenticated user IDs rather than storing passwords.

### 3.1 Relationships

- One authenticated user can submit multiple reports.
- A report can have multiple AI screening attempts.
- A report can have multiple status-history entries.
- A report can have multiple administrative reviews.
- A user can have an assigned application role.
- Anonymous reports have no authenticated reporter ID but use a protected tracking credential.

## 4. Table Definitions

The SQL types and constraints below describe the intended PostgreSQL design. Exact migrations and policies will be finalized during implementation.

### 4.1 `reports`

The primary record for every submitted road-damage report.

| Column | Proposed type | Required | Purpose |
|---|---|---|---|
| `id` | `uuid` | Yes | Primary key generated by the database |
| `reporter_user_id` | `uuid` | No | References `auth.users.id` for registered reporters |
| `tracking_token_hash` | `text` | No | Hash of the anonymous tracking secret; never returned publicly |
| `description` | `text` | No | Optional description supplied by the reporter |
| `latitude` | `double precision` | Yes | Latitude of the reported location |
| `longitude` | `double precision` | Yes | Longitude of the reported location |
| `location_label` | `text` | No | Optional human-readable location label |
| `photo_storage_path` | `text` | Yes | Storage object path for the submitted photograph |
| `lifecycle_status` | `report_status` | Yes | Current workflow state; defaults to `Submitted` |
| `verification_status` | `verification_status` | Yes | Current review/verification state; defaults to `Unverified` |
| `is_sample` | `boolean` | Yes | Identifies demonstration-generated records; defaults to `false` |
| `created_at` | `timestamptz` | Yes | Server-generated submission timestamp |
| `updated_at` | `timestamptz` | Yes | Updated when relevant report fields change |

**Constraints and validation**

- `id` is the primary key.
- `reporter_user_id` references `auth.users(id)` and becomes null if the associated account is deleted, subject to the chosen account-deletion policy.
- At least one reporter mechanism must be present: an authenticated user association or a valid anonymous tracking-token hash. Both may be present only if the final submission flow explicitly supports account-linked tracking.
- Latitude must be between `-90` and `90`.
- Longitude must be between `-180` and `180`.
- Description length must be limited by a server-enforced maximum.
- Location labels must also have a reasonable server-enforced length limit.
- A report must reference a successfully uploaded, validated photograph.
- New reports start with lifecycle status `Submitted` and verification status `Unverified`.
- `is_sample` must be set through a trusted process, not accepted as an unrestricted client-controlled flag.
- Anonymous tracking secrets must never be stored in plaintext.

The exact image-size limit, accepted image formats, and description-length limit remain implementation decisions.

### 4.2 Report Lifecycle Status

Proposed PostgreSQL enum: `report_status`.

Allowed values:

- `Submitted`
- `Under Review`
- `In Progress`
- `Resolved`
- `Rejected`

Definitions:

| Status | Meaning |
|---|---|
| `Submitted` | The application has accepted the report |
| `Under Review` | The report is being examined in the demo workflow |
| `In Progress` | The report is marked as being addressed within the demo workflow |
| `Resolved` | The report is marked resolved within the application |
| `Rejected` | The report has been determined invalid or unsuitable for inclusion |

These statuses do not prove that a municipal authority received, acknowledged, or acted on the report.

The backend should validate permitted status transitions and require a trusted administrative operation for changes that citizens are not allowed to make.

### 4.3 Verification Status

Proposed PostgreSQL enum: `verification_status`.

Initial required value:

- `Unverified`

**Proposed additional values for review:**

- `Reviewed`
- `Confirmed`
- `Disputed`

These additional values require explicit product approval before implementation. Their definitions and allowed transitions must be documented before they are exposed in the UI.

Verification is independent of lifecycle status. For example, a report can remain `Submitted` while `Unverified`, or be `Under Review` while an administrator examines its details.

AI screening alone must not automatically set a report to `Confirmed`.

### 4.4 `ai_screenings`

Stores individual screening attempts rather than overwriting every previous result.

| Column | Proposed type | Required | Purpose |
|---|---|---|---|
| `id` | `uuid` | Yes | Primary key |
| `report_id` | `uuid` | Yes | References `reports.id` |
| `screening_status` | `screening_status` | Yes | State of the screening attempt |
| `suggested_damage_type` | `text` | No | Model-suggested category, if supported |
| `suggested_severity` | `text` | No | Optional severity estimate, only if supported |
| `confidence_score` | `real` | No | Optional model confidence value when meaningful and available |
| `model_name` | `text` | No | Model identifier |
| `model_version` | `text` | No | Model version when known |
| `error_code` | `text` | No | Safe, structured error category |
| `error_summary` | `text` | No | Sanitized diagnostic summary; must not contain secrets |
| `started_at` | `timestamptz` | Yes | Screening start time |
| `completed_at` | `timestamptz` | No | Completion time, if completed |

Proposed screening states:

- `Pending`
- `Completed`
- `Uncertain`
- `Failed`

**Rules**

- A report can exist without a completed screening record.
- Screening may run asynchronously after report creation.
- Failed attempts may be retried without creating another report.
- Each retry creates a new screening record so earlier outcomes remain traceable.
- `Completed` means the screening process returned a result, not that the result is correct.
- A confidence score must be within the range supported by the selected model, normally `0` to `1` when that is the model's actual output convention.
- Severity must remain null if the selected model does not support a meaningful severity estimate.
- Public views must label outputs as AI suggestions.
- Provider credentials, raw secrets, and unnecessary image data must not be stored in error messages.

The exact damage categories, severity vocabulary, model identifier, and inference runtime remain open until model selection and testing.

### 4.5 `user_roles`

Stores application roles separately from user profile data.

| Column | Proposed type | Required | Purpose |
|---|---|---|---|
| `user_id` | `uuid` | Yes | Primary key and reference to `auth.users.id` |
| `role` | `app_role` | Yes | Assigned application role |
| `created_at` | `timestamptz` | Yes | Role-assignment timestamp |

Proposed role enum:

- `citizen`
- `admin`

Citizens do not need a manually inserted role to authenticate or submit a report. The role table exists to grant specific application privileges, particularly administrative access.

**Security requirements**

- A user must not be able to grant themselves the `admin` role.
- Role assignment and removal must use a trusted administrative process.
- The frontend must never be the source of truth for administrator privileges.
- Role checks must be enforced on every protected database operation and server-side function.
- Service-role credentials must never be exposed to the browser.

### 4.6 `report_status_history`

Records important changes to a report's workflow and verification states.

| Column | Proposed type | Required | Purpose |
|---|---|---|---|
| `id` | `uuid` | Yes | Primary key |
| `report_id` | `uuid` | Yes | Related report |
| `actor_user_id` | `uuid` | No | Authenticated user responsible for the change, if applicable |
| `change_type` | `text` | Yes | Lifecycle or verification change |
| `old_value` | `text` | No | Previous value |
| `new_value` | `text` | Yes | New value |
| `reason` | `text` | No | Optional explanation for the change |
| `created_at` | `timestamptz` | Yes | Server-generated event timestamp |

The backend should create a history entry in the same transaction as the corresponding state change where practical.

History records should not be directly editable or deletable by ordinary users. Public users should not receive unrestricted access to this table.

### 4.7 `report_reviews`

Records administrative review activity and corrections without modifying the original AI output.

| Column | Proposed type | Required | Purpose |
|---|---|---|---|
| `id` | `uuid` | Yes | Primary key |
| `report_id` | `uuid` | Yes | Report being reviewed |
| `reviewer_user_id` | `uuid` | Yes | Authenticated administrator performing the review |
| `decision` | `text` | Yes | Review outcome or action |
| `corrected_damage_type` | `text` | No | Human-corrected damage category |
| `corrected_severity` | `text` | No | Human-corrected severity, if applicable |
| `reason` | `text` | No | Explanation, including rejection reason where applicable |
| `created_at` | `timestamptz` | Yes | Review timestamp |

The `decision` field must be constrained to a documented set of values before implementation. It must not be an unrestricted mechanism for changing any report field.

A review record does not automatically mean the report is resolved. A reviewer may correct an AI suggestion, request further review, reject a report, or update verification status through explicitly authorized operations.

The original AI output must remain available in `ai_screenings` for comparison and audit.

## 5. Anonymous Tracking Security

Anonymous tracking requires a secret that is separate from the public report identifier.

### Proposed flow

1. The backend generates a cryptographically secure, unpredictable tracking token.
2. The backend stores only a suitable hash of the token in `reports.tracking_token_hash`.
3. The raw token is returned to the reporter only after the report is successfully created.
4. The reporter saves the token to track the report later.
5. A protected backend operation hashes and checks the supplied token, then returns only approved tracking information.
6. Invalid lookups return a generic response without exposing unrelated report details.

### Security requirements

- The public report UUID must not function as a tracking secret.
- Tracking tokens must have sufficient entropy to resist guessing.
- Token comparisons must use a suitable secure implementation.
- Tracking lookups should be rate-limited.
- The raw tracking token must not appear in database logs, analytics, URLs, or public API responses.
- The tracking-token hash must never be exposed through public report views.
- The tracking token must not grant administrative privileges or permit arbitrary report updates.
- Anonymous tracking should be handled through a trusted backend operation rather than an unrestricted table query.

Token length, expiration, regeneration, and rate-limiting thresholds remain implementation decisions.

## 6. Photograph Storage

Supabase Storage is the proposed storage service. The final bucket configuration remains to be implemented and verified.

### 6.1 Upload flow

1. Validate the selected file on the client for usability.
2. Validate file type, size, and relevant image properties on the backend.
3. Upload through an authorized storage operation.
4. Create the report only when the photograph has been successfully stored and its reference validated.
5. If report creation fails after upload, clean up the orphaned object where safely possible.
6. If screening fails after report creation, retain the report and photograph.

The application must not display successful submission until the backend confirms the report record exists and references a valid photograph.

### 6.2 Public visibility

The product requirements intend submitted photographs to be viewable alongside public reports.

This means the storage design must intentionally support public viewing of approved report images while protecting private metadata and internal records. Public image access must not expose unrelated files or privileged data.

Before implementation, select and document either:

- A dedicated public-image bucket with strict upload controls and non-guessable object paths; or
- Private storage with a trusted mechanism for issuing access to approved public report images.

The selected approach must be tested against the intended public-map experience. The team must not assume that a random object path alone makes a public bucket private.

### 6.3 Privacy disclosure

The reporting interface must explain that uploaded photographs may be publicly visible. Automatic blurring of faces and vehicle registration plates is not guaranteed in the MVP.

The schema does not claim that photographs are automatically anonymized or moderated.

## 7. Row-Level Security (RLS)

RLS must be enabled on all application tables accessible through Supabase's client-facing APIs.

The following policy matrix describes the intended permissions. Exact SQL policies must be tested during implementation.

| Resource | Public visitor | Registered citizen | Administrator |
|---|---|---|---|
| Public report fields | Read eligible public reports | Read eligible public reports | Read reports permitted for review |
| Private report-management data | No direct access | Read only their own permitted data | Access only as required for review |
| Report creation | Through trusted submission flow | Through trusted submission flow | Through authorized operations where needed |
| Own report history | No account history | Read own reports | Read according to authorized review needs |
| AI screening details | Read only fields approved for public display | Read permitted details for own reports | Read screening details needed for review |
| Administrative review records | No access | No access to internal records | Authorized access |
| Status history | No unrestricted table access | No unrestricted table access | Authorized access |
| Role assignments | No access | No role-management access | Role management through a separately protected process |

### 7.1 Public access

Public map access must not require an account.

Expose an explicit public-report view or trusted query that returns only approved fields, such as:

- Report ID.
- Public photograph reference.
- Coordinates and approved location label.
- Optional public description.
- Submission timestamp.
- Lifecycle status.
- Verification status.
- Approved AI screening summary.
- Sample-data indicator.

Do not expose:

- Anonymous tracking-token hashes.
- Private account details.
- Authentication information.
- Internal administrative notes.
- Privileged configuration or credentials.
- Unfiltered internal error details.

The public API must apply the product's visibility rules, including how rejected reports are handled. Rejected reports should not remain publicly visible by default unless the product explicitly adopts a different policy.

### 7.2 Registered citizens

Authenticated citizens may view their own report history and the permitted details of their reports.

Access must be scoped to the authenticated user's ID. Knowing another report's UUID must not permit access to private report-management information.

### 7.3 Administrators

Administrative access must be checked by trusted backend authorization. An administrator-only screen or hidden navigation item is not sufficient.

The implementation should use a carefully designed role-checking function or equivalent policy mechanism that avoids recursive RLS evaluation and prevents users from modifying their own privileges.

Administrative updates should be performed through explicitly authorized operations, with validation and audit history.

### 7.4 Trusted operations

Supabase Edge Functions or equivalent trusted operations should handle tasks that require secrets, token verification, role checks, or coordinated writes.

The Supabase service-role key must never be used in browser code. If a trusted function uses elevated database access, it must independently authenticate the caller where relevant and enforce the intended authorization rules.

## 8. Submission and AI Processing Transactions

The backend must define clear behavior for partial failures.

### 8.1 Report creation

A report is accepted only after the backend confirms that the report record was created and its required photograph reference is valid.

The backend should avoid leaving a report in a state that appears successfully submitted when the associated upload or record creation failed.

Where multiple operations cannot share one database transaction, use explicit cleanup and retry behavior.

### 8.2 AI screening

AI screening should be initiated after, or in coordination with, successful report creation.

The report must remain valid if:

- The model runtime is unavailable.
- Inference times out.
- The model returns an uncertain result.
- The selected model does not support severity estimation.
- A screening retry fails.

The application should communicate the screening state separately from submission success.

### 8.3 Administrative updates

Changes to lifecycle or verification state should be validated and recorded. The operation should update the report and its history consistently.

If a write fails, the interface must not claim that the change was saved.

## 9. Indexes and Query Performance

The following indexes are proposed for common MVP queries:

- Primary-key indexes for all tables.
- `reports(reporter_user_id, created_at DESC)` for a registered citizen's report history.
- `reports(lifecycle_status, created_at DESC)` for administrative queues.
- `reports(verification_status, created_at DESC)` for review filtering.
- A suitable geographic index for map queries if PostGIS is adopted.
- `ai_screenings(report_id, started_at DESC)` for retrieving screening attempts.
- `report_status_history(report_id, created_at DESC)` for report history.
- `report_reviews(report_id, created_at DESC)` for review records.
- A unique index on the anonymous tracking-token hash when a token is present.
- `user_roles(user_id)` for role checks.

A simple latitude/longitude bounding-box query may be adequate for an initial demonstration. If PostGIS is available and selected, a geographic column and spatial index may be preferable.

The implementation must select a map-query approach that is supported by the actual Supabase project configuration.

## 10. Sample and Test Data

The database must distinguish demonstration-generated sample records from real test submissions.

- Real submissions default to `is_sample = false`.
- Sample data is created through a trusted seeding or administrative process.
- Public UI responses must include enough information to display an explicit sample-data label.
- Sample records must not be presented as verified municipal reports.
- Test data must not contain real users' private information.
- Seeding and cleanup operations must avoid deleting genuine test submissions.
- The mechanism used to create or remove sample records must not be available to ordinary citizens.

A boolean `is_sample` flag is sufficient for the initial demo. Additional provenance fields may be added later if the project needs richer data lineage.

## 11. Error Handling and Operational Requirements

Backend operations should return understandable, structured errors without exposing secrets or internal implementation details.

Expected error categories include:

- Invalid or missing input.
- Unsupported or oversized image.
- Upload failure.
- Report-creation failure.
- Authentication required.
- Unauthorized operation.
- Invalid tracking token.
- AI screening pending, uncertain, or failed.
- Invalid status transition.
- Temporary backend or network failure.

Operational rules:

- A failed AI request must not delete a saved report.
- A failed upload must not create a report that appears complete.
- A failed report creation must not return a valid tracking token as if submission succeeded.
- A failed administrative update must not be shown as saved.
- Internal logs must not contain raw tracking tokens or privileged credentials.
- The frontend must distinguish retryable failures from invalid input where practical.

## 12. Testing Requirements

Before the schema is considered implementation-ready, test the following cases.

### Reporting

- Anonymous submission creates a report with a tracking-token hash.
- Registered submission links the report to the authenticated user.
- Missing photographs and invalid coordinates are rejected.
- An unsuccessful upload does not produce a completed submission.
- An AI failure does not prevent a valid report from being retained.

### Tracking and privacy

- The correct anonymous token returns only permitted tracking details.
- An invalid token reveals no unrelated report information.
- A public report UUID alone cannot retrieve private tracking data.
- Public responses do not contain token hashes, private account data, or internal administrative notes.

### Authorization

- One citizen cannot read another citizen's private report-management data.
- A citizen cannot assign themselves the administrator role.
- An unauthenticated visitor cannot perform administrative actions.
- Administrative operations reject callers without the required role.
- Direct API calls cannot bypass the intended RLS restrictions.

### AI screening

- Pending, completed, uncertain, and failed states are represented correctly.
- Unsupported severity estimates are not fabricated.
- A retry creates a traceable screening attempt.
- Original AI output remains distinguishable from human corrections.

### Administrative review and history

- Unauthorized users cannot alter report status.
- Valid status changes create corresponding history entries.
- Invalid status transitions are rejected.
- Rejection reasons are recorded where required.
- Sample-data records remain distinguishable from real submissions.

## 13. Open Decisions Before Implementation

The following decisions remain unresolved and must not be silently treated as finalized:

1. **Verification values:** Confirm whether the proposed `Reviewed`, `Confirmed`, and `Disputed` values are necessary for the MVP.
2. **Tracking-token lifecycle:** Choose token format, entropy, expiration policy, and rate-limiting implementation.
3. **Storage access:** Choose the public or private-bucket approach and define exact image-access rules.
4. **Image validation:** Finalize allowed formats, maximum file size, and upload limits.
5. **Damage categories and severity:** Define the accepted category vocabulary after selecting and evaluating the model.
6. **AI confidence:** Decide whether the selected model's confidence output is meaningful enough to store and display.
7. **Geographic queries:** Decide whether the initial implementation uses coordinate bounding boxes or PostGIS.
8. **Administrative review decisions:** Define allowed review actions and valid status transitions.
9. **Rejected-report visibility:** Confirm the public visibility policy for rejected reports.
10. **Account deletion:** Decide whether reports remain associated with a deleted account, are anonymized, or follow another policy.
11. **Sample-data management:** Choose the trusted seeding and cleanup procedure.
12. **Storage cleanup:** Define how abandoned uploads and failed submissions are detected and cleaned up.

These decisions should be resolved before the corresponding implementation is finalized.

## 15. Definition of Done

`BACKEND_SCHEMA.md` is ready to guide implementation when:

- The table definitions and relationships are approved.
- Lifecycle, verification, and AI screening states are explicitly defined.
- Anonymous tracking does not depend on a public report ID.
- Public and private data boundaries are documented.
- Administrative authorization is enforced server-side.
- Photograph storage and partial-failure behavior are specified.
- Important changes are auditable.
- Open decisions affecting implementation are resolved or explicitly deferred.
- The implementation team can derive migrations and security tests without inventing undocumented data rules.

Approval of this document establishes an agreed design baseline; it does not establish that the schema or application has been implemented or verified.
